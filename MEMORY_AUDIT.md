Цель: 100–150 МиБ для всего дерева приложения, включая Mihomo. Если лимит
относится к одному процессу, результаты нужно оценивать отдельно по PID.
Все размеры ниже — МиБ (1 048 576 байт), кроме размеров JS-файлов.

## Вывод

Наблюдаемые ~350 МиБ воспроизведены на уже запущенной установленной версии:
сумма приватной физической памяти составила **349,0 МиБ**. Основной потребитель —
GPU-процесс, а не JavaScript или журнал. Уменьшение JS-бандла полезно, но само
по себе не обеспечит целевой бюджет.

В изолированном тесте текущего production-renderer отключение GPU снизило
приватную физическую память с **263,9 до 124,1 МиБ** на главном экране.
После переходов и открытия редактора программный режим достиг **165,0 МиБ**.
Таким образом, стабильные 100–150 МиБ с открытым интерфейсом и реальным VPN
пока **не подтверждены**. Режим без окна и программный рендеринг — наиболее
перспективный путь к этому бюджету в фоне.

## Что именно измерялось

| Метрика | Значение и ограничения |
| --- | --- |
| Private Working Set | Приватные страницы в физической RAM. Основная метрика этого аудита; её удобно сопоставлять с отображаемой памятью в Диспетчере задач, предварительно проверив выбранную колонку. |
| Working Set | Все резидентные страницы процесса. При суммировании по PID общие страницы могут учитываться повторно. |
| Private Bytes / commit | Приватная выделенная память, включая страницы вне физической RAM. Это не Private Working Set. |
| JS heap | Только JavaScript renderer. Не включает GPU, большую часть нативной памяти, Chromium и ядро. |

Electron возвращает `workingSetSize` и `privateBytes` в КиБ:
[MemoryInfo](https://www.electronjs.org/docs/latest/api/structures/memory-info).
Private Working Set получен отдельно из
`Win32_PerfFormattedData_PerfProc_Process.WorkingSetPrivate`.
Снимки Electron и Windows снимаются последовательно, поэтому возможны небольшие расхождения.

## Изолированный production-бенчмарк

Electron 44.9.1, окно 1040 × 720 DIP, фактический `devicePixelRatio = 2`,
production-сборка без DevTools. Интерфейс работает с IPC-фикстурой:
18 узлов, 210 правил и 8 соединений. Отдельно запускается настоящий Mihomo
с 20 000 тестовых DOMAIN-правил, без TUN и системного прокси. Этот Mihomo
не обслуживает фикстуру интерфейса. Main-сервисы приложения в стенде не запускаются.
Это сравнение режимов renderer, а не полноценный end-to-end замер VPN.

## Найденные причины и приоритеты

1. **GPU/композитинг — главный приоритет.** Отключение ускорения существенно
   снижает приватную память на этой машине. Настройка `disableGpu` уже есть
   в приложении и применяется после перезапуска. Не изменён её default:
   программный режим нужно дополнительно проверить на плавность resize,
   прокрутку и CPU. Эти характеристики в данном аудите не измерялись.

2. **Скрытие окна сохраняет Chromium renderer.** `WindowService` вызывает
   `hide()`, останавливает потоки и снимает глобус, но не уничтожает окно.
   Уже существующий режим «Только ядро» вызывает `destroy()`. Для фоновой цели
   100–150 МиБ стоит использовать его вместе с проверенным режимом рендеринга;
   затем рассмотреть автоматическую выгрузку окна после периода бездействия.
   Такое поведение потребует сохранения несохранённых правок и восстановления
   выбранной страницы. В текущем изменении оно не вводилось.

3. **Редактор ошибочно попадал в стартовый vendor-чанк.** В
   `electron.vite.config.ts` условие `id.includes('react')` также совпадало с
   `@uiw/react-codemirror`, Radix и пакетами иконок. Исправлено точное
   сопоставление каталогов пакетов. `vendor-react` уменьшился с **795,95 до
   223,62 КБ**, CodeMirror теперь загружается через ленивые страницы/диалоги.
   Это подтверждённое уменьшение стартового кода, а не доказанная экономия
   сотен МиБ RAM. Для точной небольшой дельты RAM нужны повторные A/B-прогоны.

4. **Полный список правил хранится даже вне страницы правил.**
   `useRulesStore` загружает его после обновлений данных; dashboard использует
   правила для описания маршрутов. `RulesPage` дополнительно создаёт копии
   всех правил перед фильтрацией, хотя показывает по 100 строк. Для крупных
   профилей следующий шаг — компактная сводка для dashboard и загрузка полного
   массива по запросу страницы, с фильтрацией/пагинацией в main. Экономия
   зависит от реального размера профиля; в этом аудите не измерена.

5. **Снимки соединений проходят через main → IPC → renderer.** Их стоимость
   растёт с количеством соединений; таблица и dashboard получают полный
   snapshot. Следующий шаг при большом числе соединений — отдельная сводка
   трафика/маршрутов для главной и ограниченный список для таблицы. Сохранение
   точного расчёта прямого/VPN-трафика необходимо проверить отдельно.

6. **Лимит V8 не является лимитом RAM приложения.**
   `--max-old-space-size=128` ограничивает old space, но не GPU, нативную память
   Chromium или Mihomo. Уменьшать его ради общего бюджета без heap-профиля
   нецелесообразно. `trimProcessMemory()` очищает HTTP-cache и запускает GC main;
   это не гарантирует освобождение графических ресурсов или уменьшение RAM
   до заданного значения.

Уже сделано разумно: страницы и диалоги загружаются лениво, журнал ограничен
по числу записей, polling соединений приостанавливается вне нужных экранов,
при скрытии очищаются снимки соединений и кэши профиля, GeoIP-worker завершается
после простоя, canvas глобуса освобождает буфер при размонтировании.
Заменять эти механизмы без измерений не требуется.

## Как повторить и проверить цель

```powershell
pnpm build
$env:MEMORY_CORE = '1'
$env:MEMORY_SOFTWARE = '0'
pnpm exec electron scripts/measure-memory.cjs hardware
$env:MEMORY_SOFTWARE = '1'
pnpm exec electron scripts/measure-memory.cjs software
```

Для варианта без глобуса дополнительно установить `MEMORY_LITE=1`.
Для проверки голого Electron-интерфейса — `MEMORY_CORE=0`.
Основная колонка JSON: `totalPrivateWorkingSetMiB`.
`privateMB`/`totalPrivateMiB` означают commit; `workingSetMB`/`totalWorkingSetMiB`
означают Working Set, а не приватную физическую память.

Критерий для следующего этапа: production-приложение с реальной подпиской,
TUN/прокси и обычной нагрузкой, 30–60 минут работы, несколько открытий редактора
и циклов скрытия/показа. Записывать Private Working Set и commit каждого PID,
CPU и отзывчивость. Отдельные бюджеты нужны для открытого окна и режима в трее.
До этого обещать стабильные 100–150 МиБ для всего приложения нельзя.

Методика соответствует рекомендации Electron сначала профилировать реальные
потребители и откладывать ненужную загрузку:
[Electron Performance](https://www.electronjs.org/docs/latest/tutorial/performance).

## Продолжение: оптимизация исходников

После аудита реализованы пункты по удержанию данных. Установленный VPN,
его настройки и выбор GPU не изменялись.

- `mihomo.getRules('summary')` сокращает список в main до первого правила
  каждого outbound и первого `MATCH` **до передачи через IPC**. Порядок
  сохраняется, поэтому существующие подписи маршрутов получают те же результаты
  поиска. В тесте 20 001 правило сворачивается в 3 записи. Размер сводки зависит
  от числа различных outbound; это не фиксированный лимит в 3 записи.
- Dashboard запрашивает сводку, страница правил — полный список. В лёгком
  режиме главной и на остальных страницах правила не загружаются. При скрытии
  окна или уходе со страницы соответствующий массив освобождается. Поздние
  ответы от предыдущей страницы игнорируются.
- Таблица правил хранит индексы результатов фильтрации и создаёт объекты только
  для текущих 100 строк вместо копирования каждого правила. Поиск без запроса
  больше не создаёт строку для каждого правила. Исходные номера сохранены.
- Снимки соединений освобождаются при переходе на страницы, которым они не нужны.
  Отображаемый массив журнала освобождается при уходе с журнала; ограниченный
  буфер истории сохраняется для возврата на страницу.

Ограничение: полный ответ `/rules` всё ещё временно разбирается в main.
При возвращении на страницу правил он загружается снова; это обмен постоянного
удержания данных на загрузку по запросу. Проблема графической памяти этим
изменением не решается.

### Сравнение на 50 000 тестовых правил

Оба прогона: GPU отключён, отдельный тестовый Mihomo включён, одинаковая
фикстура с 50 000 DOMAIN-правил и завершающим MATCH. До изменений сохранена
предыдущая production-сборка renderer; использован тот же измерительный стенд.
Размер тестового профиля ядра остался 20 000 правил, как в первом аудите.

| Сценарий | Private Working Set до → после, МиБ | JS heap до → после, МиБ |
| --- | ---: | ---: |
| Главная | 140,8 → **127,9** | 19,7 → **12,1** |
| Настройки | 148,4 → **127,4** | 29,7 → **14,0** |
| После циклов навигации | 158,6 → 148,1 | 18,7 → 19,5 |
| Открыта страница правил | 142,5 → 162,5 | 16,0 → 27,6 |
| Главная после редактора | 152,0 → 186,1 | 18,8 → 32,9 |
| Скрытое окно после диагностического GC | 140,9 → **136,6** | 16,0 → **12,4** |

Стартовая память уменьшилась в этом прогоне примерно на 13–21 МиБ. После
загрузки полного списка кратковременный расход, напротив, вырос: моменты GC
различаются, а повторная загрузка создаёт временные объекты. После GC живой
heap меньше на 3,6 МиБ, что подтверждает снижение удержания данных, но **не
гарантирует снижение каждого пика RAM**. Это одна пара прогонов; точные дельты
не следует считать стабильным нормативом. GC в production не добавлялся.

Артефакты: `artifacts/memory/retention-before-50k.json` и
`artifacts/memory/retention-after-50k.json`.
Для повторения задать `MEMORY_RULE_COUNT=50000`; `MEMORY_RENDERER_FILE` позволяет
выбрать HTML сохранённой baseline-сборки. Эти числа относятся к изолированному
стенду, не к установленному приложению.

Проверены: production build, TypeScript, ESLint изменённых файлов,
`test:bundle`, `test:loading`, `test:geo`, `test:kernel`, `test:settings`.
Добавлен и пройден `pnpm test:rules:ui`: сводка на главной, полный список правил,
пагинация, поиск, фильтрация по типу, исходные номера строк и повторный вход
на страницу. Тест включён в UI-suite. Полный UI-suite не объявляется пройденным:
ранее установленный сбой `traffic fades after activity` остаётся открытым.

Итоговый бюджет 100–150 МиБ для работающего VPN пока не достигнут и не подтверждён.
Главный оставшийся фактор — GPU; изменения исходников устраняют лишнее удержание
данных без принудительной смены режима рендеринга.
